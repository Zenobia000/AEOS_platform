## 3. 各 Blocker 細項

### 3.1 #1 — S1-4 OBS infra (Prom+Grafana+Loki on Hetzner)

**背景**：OBS-001 §10 規定 W1 必交付「Prometheus + Grafana + Loki on Hetzner；service 出 Golden Signals」。沒有觀測，prod 部署等於黑盒。

**為何卡**：
- Hetzner Cloud 帳號未開（需信用卡、公司資訊）
- 沒 API token 無法跑 IaC（Terraform / Pulumi）
- VM 開機前 nginx + TLS + Compose stack 都無處部署

**解鎖步驟**：
1. CEO 確認預算（Phase 1 infra 月支出目標 < $150，依 COST-MODEL）
2. CTO 開 Hetzner Cloud Account（含 invoice 與 VAT 設定）
3. 開 1 台 CX22（2 vCPU / 4 GB / 40 GB SSD，€4.5/月）作 observability stack 專屬 VM
4. Cloudflare DNS 一筆 A record 指向 VM
5. 部署 docker-compose for prometheus/grafana/loki/tempo（用 grafana/lgtm stack 一鍵就好）
6. FastAPI app 加 `prometheus-fastapi-instrumentator`，把 /metrics placeholder 換掉

**解鎖後第一個動作**：把 OBS-001 §10 W1 checklist 在 LAUNCH-DASHBOARD §「Engineering Health」相關 row 從 n/a 轉成實值。

### 3.2 #2 — S1-6 RLS policy 實作

**背景**：ADR-0007 規定 Phase 1 多租戶採「共享 PG + Row Level Security + 應用層雙重檢查」。

**為何卡**：DB 還沒有任何表，RLS 政策無物可附。這不是真的 blocker，是「太早」。

**解鎖路徑**：S2 第一支 Alembic migration 建出第一張帶 `tenant_id` 的表（如 `tenant` / `api_key`）後，立即在同一個 migration 內 ENABLE RLS 並建立 policy template。後續每張表都套同一個 pattern。

**解鎖後第一個動作**：寫 RLS 應用層 middleware（SQLAlchemy session-scoped variable 注入 current_setting('app.tenant_id')），並寫 `tests/test_rls_isolation.py` cross-tenant query 測試（對應 SEC-001 §6.1 #4）。

### 3.3 #3 — S1-6 HMAC webhook 驗簽

**背景**：API-002 規定 LINE webhook 進來必驗 HMAC-SHA256（`X-Line-Signature`），驗簽失敗 → 403 + audit。對應 SEC-001 §6.1 #1。

**為何卡**：沒有 LINE Channel Secret 就無法寫單元測試與整合測試。

**解鎖路徑**：
- **不必等 pilot**：CTO 可立即在 LINE Developers Console 開一個 sandbox channel（免費）拿 Channel Secret，先寫驗簽 code + 測試
- pilot 簽下後再切換到客戶提供的真實 Channel Secret

**解鎖後第一個動作**：把驗簽 code 寫進 `app/channels/line.py`（S4 開工時建立），對應的單元測試 fixture 用 dummy secret。

### 3.4 #4 — S1-6 TLS (nginx + Let's Encrypt)

**背景**：SEC-001 §6.1 #8 要求「TLS 1.2+ only + HSTS + 證書自動續期」。

**為何卡**：與 #1 共用 — 沒有 server 就沒 TLS 可設。

**解鎖路徑**：拿到 Hetzner VM（#1 解鎖）+ Cloudflare DNS（同步申請）後，nginx + certbot 一個 docker-compose service 即可。

**解鎖後第一個動作**：寫 `infra/nginx/aeos.conf` template（含 HSTS header），certbot 自動續期 cron。

### 3.5 #5 — S1-7 Oncall 接線 (Slack + PagerDuty)

**背景**：RUNBOOK-001 §1~§3 要求 P0 5 分鐘內 ack、P1 15 分鐘內 ack；通報路徑經 Slack + PagerDuty。

**為何卡**：
- 公司 Slack workspace 還沒建（CEO/CTO 個人 Slack 不算工作 workspace）
- PagerDuty 訂閱還沒開（Free tier 5 user 內免費，需註冊）

**解鎖步驟**：
1. CEO 用 `funngo.ai` domain 開 Slack workspace（Free plan 起步）
2. 建 channels：`#engineering`、`#oncall`、`#alerts`、`#general`
3. CEO 註冊 PagerDuty Free（個人 email 即可）
4. CTO 接 primary oncall schedule、設 escalation policy
5. Alertmanager（S1-4 解鎖後）→ PagerDuty webhook 接好

**解鎖後第一個動作**：跑一次 dummy P1 alert 端到端（Alertmanager → PagerDuty → CTO 手機通知）。

### 3.6 #6 — S2~S8 全部產品 code

**背景**：LAUNCH-DASHBOARD line 52 顯示 `Pilot 客戶簽約數 = 0 / 目標 3-5 家`。S2 IN PROGRESS 的硬 gate 是「需已簽 pilot 客戶」（同檔 line 23）。

**為何卡**：
- PRD-001 整份產品圍繞「7 天上線一位 AI 客服」設計，沒有客戶 = 沒有 KB / Test set / LINE channel / Expert，所有 sprint exit gate（AC-001~005）都無法驗證
- 連內部 dogfood 都需要假設一個業務情境，效果不如真實客戶 KB
- LAUNCH-DASHBOARD §「CEO 本週行動」line 43 列「簽第一個 Pilot 客戶」為 CEO 本週第一優先；PILOT-ICP §3.1「目前全空白，目標 30 個 ICP-matched 候選」表示連 pipeline 都還沒開始

**解鎖步驟（CEO 視角）**：
1. 完成 PILOT-ICP-2026-05 §3.1：填入 30 個 ICP-matched 候選客戶名單
2. 對 30 名單做第一輪外觸（cold outreach + 引薦）
3. 約 5 家深入 demo（用 PRD-001 + BF-001 解釋 7 天路徑）
4. 簽下第一家：50% setup fee 入帳 + LINE OA credentials + KB 來源
5. 通知 CTO 啟動 S2

**解鎖後第一個動作**：CTO 依 KICKOFF-CHECKLIST §G 收齊 pilot 資訊 → 切 `feat/s2-kb-ingest` branch → 動 FastAPI Tenant aggregate + Alembic migration。

**沒解鎖的代價**：
- 簽約延後 1 週 → 整 Phase 1 時間軸右移 1 週（13 → 14 週）
- 簽約延後 4 週 → Phase 1 預算 ~$35K 跑道吃緊（COST-MODEL §3）；可能需擴張 runway
- 簽約延後 8 週 → 重新評估 PRD-001 是否需要 pivot
